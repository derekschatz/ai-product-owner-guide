01 · Start here

The basics, in plain English

Nine terms that explain most of what you will run into. The analogies are shortcuts, not perfect technical definitions, but they make the tools easier to reason about.

Model
Think of the large language model, or LLM, as the brain. It is the engine underneath the chat window. It has read an enormous amount of text and predicts what should come next, one word at a time. That is why it is fluent, fast, and occasionally confident about something wrong. Treat it like a well-read colleague, not a database.

Which one to pick: most tools let you choose a model from a dropdown. Use the newest or most capable option for real work; the "fast" or "mini" options are for quick, low-stakes questions.

Prompt
Whatever you type. The quality of the answer tracks the quality of the request. Situation, goal, audience, constraints, and what a good answer looks like all count. Vague in, generic out.
Chat vs. Project
A chat is one conversation. When it ends, most of what you said goes with it. A Project is like a project room: the brief, reference files, instructions, and related conversations stay together. Use a Project for anything you will return to: your product, your customers, your backlog.

Where to find it: ChatGPT calls them Projects. Claude calls them Projects. Microsoft 365 Copilot uses Notebooks, and a saved brief you paste in works too. See the tool guide.

Context window
Everything the model can "see" right now: your messages, attached files, and its own earlier answers. It is large but not infinite. In a very long chat the early parts fade or drop out. Start a new chat when the topic changes and put anything permanent in a Project or a brief.
Hallucination
When the model fills a gap with something plausible instead of something true. Numbers, sources, quotes, names, and "how common is this" claims are the usual suspects. Ask it to use only what you gave it and to say when it does not know.
Reasoning mode
A setting that lets the model think longer before answering. Slower, better for analysis, tradeoffs, and anything with several moving parts. Skip it for simple rewrites.

Where to find it: ChatGPT has a "Think longer" option and reasoning models. Claude calls it Extended thinking. Copilot calls it Think Deeper.

Custom instructions
Instructions are like a job description and operating manual. They tell the AI who it is helping, how to work, how to format answers, and what to avoid. Set them once and stop repeating yourself. A Project can have instructions that apply only inside that Project.
Skill
Skills are like SOPs for AI. A skill is a reusable set of instructions for one kind of work, such as synthesizing feedback or critiquing a backlog. A good skill names the inputs, steps, output, and guardrails so the process is repeatable. See how to make one.
Tool
Tools are like hands and access badges. The model can reason with language; a tool lets it do something, such as search the web, read a file, run code, or use another app. Access should match the job and your organization's policy.
Agent
A model that can take actions, not just answer: browse, open files, run steps in sequence, use other software. You will hear the word a lot. For PO work today, the chat and a Project cover most of what matters. Agents are worth watching, not required.

02 · Get better answers

Eight habits that do most of the work

None of these require a special technique. They are the difference between a generic answer and one you can actually use.

01

Give it the situation, not just the task

Who you are, what you are trying to decide, who the output is for, and what "good" looks like. Two extra sentences of context beat ten follow-up questions.

02

Let it interview you first

"Ask me ten questions, one at a time, before you answer." This is the single most useful move from class. It pulls out the context you forgot to give.

03

Separate observation from assumption

Ask it to label which claims come from your source material and which are its own inference. This is the fastest way to catch invented detail.

04

Ask for alternatives, not the answer

"Give me three different ways" produces better thinking than "what should I do." Expand the choices before you narrow them.

05

Iterate in the same chat

Critique the draft: too long, wrong audience, missing the fallback. Each pass builds on what it already knows. Restarting throws that away.

06

Make it show its sources

"Using only these notes" and "cite where each point came from" keep it honest. If it cannot point to a source, treat the claim as a hypothesis.

07

Verify before you share

AI prepares the conversation. You still make the call. Read the output the way you would read a first draft from a new team member.

08

Save what works

When a prompt or a context brief works, keep it. Put it in a Project's instructions or a note you can paste into any tool.

03 · Part 1 from class

When AI is in the product

The product changes, so the decisions change. You now manage uncertainty after release, and the job is still maximizing value.

A normal product
  1. Define the expected behavior
  2. Release the completed behavior
  3. Measure whether customers use it
An AI product
  1. Define an acceptable range of behavior
  2. Release with evidence and a fallback
  3. Watch quality as usage changes

Should this experience use AI?

"Can we use AI?" matters less than "should we, here?" A simpler experience may still win. Tick the ones you can answer with confidence.

Nothing checked yet. Tick each question you could answer confidently in a room with your team.

Every AI story needs four answers

A happy path is no longer a complete backlog item. Decide these with your team and specialists before the story is ready.

The four answers
  • OutcomeWhat should improve for the customer?
  • QualityHow good must this behavior be? What is "good enough"?
  • BoundariesWhat must the AI refuse or avoid?
  • FallbackWhat happens when it cannot help?
Worked example: a support reply assistant
  • OutcomeAgents send a first reply faster without lowering customer satisfaction.
  • QualityDrafts are usable with light edits most of the time. A reviewer team scores samples weekly.
  • BoundariesNever promises refunds, quotes prices, or gives legal or medical guidance. Never sends without a human.
  • FallbackIf confidence is low or the topic is out of scope, show a blank reply and the relevant help article instead.

A release is one point in a longer decision

      

        
Step 1
Discover
Test whether AI adds value. Find the riskiest assumption.
What this looks like
A few customer conversations, a hand-built mock of the AI moment, and one written assumption that would kill the idea if false.

        
Step 2
Evaluate
Agree on test cases, criteria, and the failures that are not acceptable.
What this looks like
A shared list of real examples the team scores together, with a line for "never acceptable" that everyone signed off on.

        
Step 3
Release
Choose exposure, the fallback, and the evidence needed to expand.
What this looks like
A small slice of users first, a clear fallback when confidence is low, and an agreed number that tells you it is safe to widen.

        
Step 4
Adapt
Monitor value, quality, cost, and how customer behavior shifts.
What this looks like
A recurring look at sampled outputs and cost per use, and backlog items that come from what customers actually did with it.

      

      
Ordering the backlog: rank by customer value and by how much uncertainty an item removes. Both count. An item that answers "will this even work?" can outrank a bigger feature.

Frame the problem first
Framing

          
From the class activity. Let the model interview you before it suggests anything.

          
I am working on a solution to solve . My goal is to frame this problem so we can develop an effective solution. Ask me 10 questions, one at a time, so we can frame it appropriately. After the last question, summarize the problem in one paragraph and list the assumptions we are making.

          
Answer honestly. Short answers are fine.

        


        

          
Feedback synthesis
Discovery

          
Turn a pile of notes into patterns without letting the model invent how common anything is.

          
Here are interview notes: .

Using only these notes, find the recurring problems and cite which note each one came from. Separate observation from assumption. Point out anything contradictory between sources. Suggest five follow-up questions for the next interview. Do not invent frequency or impact.

          
Works with survey comments and support tickets too.

        


        

          
Backlog critic
Backlog

          
A second opinion on ordering. It will not know your team's capacity, so keep effort out of it.

          
Here is our Product Goal: .
Here are the top backlog items in order: .

Which items lack clear evidence of customer value? Surface the assumptions behind the current ordering. Point out anything that seems to be there because of who asked rather than what it delivers. Do not estimate effort.

          
Bring the output to refinement, not the ordering.

        


        

          
Stakeholder reframe
Stakeholders

          
Get from "build this feature" back to the outcome behind it before you say yes or no.

          
A stakeholder asked for  because .

What customer or business outcome sits behind this request? Give four alternative ways to reach that outcome, including at least one process change and one small experiment we could run in a sprint. For each, state the assumption it depends on.

          
Use the output to shape the conversation, not to replace it.

        


        

          
Expand the choices
Ideation

          
Instead of "give me feature ideas." Forces range before you narrow down.

          
Customer problem: .

Generate different ways to solve this. Include a process change, a simpler product change, and a bigger bet. State the assumption behind each one and what we would need to see to believe it. Then suggest one cheap experiment for the option you think is most promising, and explain why.

          
Pair with the framing prompt for best results.

        


        

          
Five ideas, fast
Ideation

          
Step 3 of the class activity. Quick and deliberately simple.

          
Generate 5 ideas that will solve this problem for the people affected: . For each idea, give it a name, describe it in two sentences, and say who benefits most.

          
Pick one as a group, then prototype it.

        


        

          
Rapid prototype
Prototyping

          
Make the idea real enough to react to: experience, product logic, and a learning plan.

          
Using this problem:  and this idea: , draft a simple end-to-end interaction. Include the happy path, two edge cases, and what happens when it cannot help (the fallback). Then write five questions I could ask a customer to test whether this is worth building. Label every assumption.

          
A prototype earns a reaction, not proof.

        


        

          
Pitch it
Prototyping

          
Step 4 of the class activity. Most tools will build a slide or one-page artifact from this.

          
Build an artifact so I can present this problem and solution to a group of investors. Problem: . Solution: . Keep it to one page or a few slides: the problem, who has it, the solution, why now, and what we would need to test first.

          
Swap "investors" for your leadership team.

        


        

          
Should this use AI?
AI in the product

          
Walk the four questions from class before anyone starts building.

          
We are considering using AI for this experience: .

Help me think it through with four questions. Customer value: which outcome improves enough to justify the added complexity? Need for adaptation: does this problem benefit from interpreting varied, ambiguous input? Available context: can the product actually access the information it needs to decide? Cost of error: what happens when the AI is wrong, unsure, or unavailable? For each, give me your honest read and what I should find out. Finish with a simpler non-AI alternative I should compare against.

          
Bring the answers to your team and specialists.

        


        

          
Four answers for an AI story
AI in the product

          
Turn a happy-path story into something the team can actually build and evaluate.

          
Here is a backlog item that involves AI: .

Draft the four answers this story needs. Outcome: what should improve for the customer? Quality: how good must the behavior be, and how would we know? Boundaries: what must the AI refuse or avoid? Fallback: what happens when it cannot help? Then list the test cases and the failures we should agree are not acceptable before release. Mark anything I need to confirm with the team.

          
Review with engineers and any specialists before it is ready.

        


        

          
Stakeholder update
Writing

          
A first draft in the reader's language, not the team's.

          
Write a short update for  about .

What happened this sprint: .
Decisions made: .
Open risks or asks: .

Lead with the outcome, not the activity. Keep it under 200 words, plain language, no jargon. Do not add anything I did not give you. Flag any sentence where you are unsure of the facts.

          
Also works for release notes and sprint review summaries.

        


        

          
Explain it to me
Framing

          
For the technical concept the team keeps mentioning that you have been nodding along to.

          
Explain  to me as a Product Owner with no engineering background. Use one everyday analogy, then tell me what it changes about the decisions I make (scope, quality, cost, risk). Keep it under 250 words, then offer to go deeper on any part.

          
Follow up with "what should I ask my team about this?"

06 · Take it back to work

      
Run the class exercise with your team

      
Frame it. Solve it. Pitch it. About 20 minutes, one screen shared, one AI chat open. It works as a refinement warm-up, a discovery kickoff, or a way to show a skeptical team what the tools can and cannot do.

      

        
Pick a problem
As a group, choose one real problem you all care about. Real beats hypothetical: the reactions are more honest.

        
Frame it
Paste the framing prompt and answer the ten questions together. Notice which ones the group disagrees on.
"I'm working on a solution to solve [problem]. My goal is to frame this problem so we can develop an effective solution. Ask me 10 questions, one at a time, so we can frame it appropriately."

        
Generate ideas, then pick one
Ask for five ideas. Discuss, then choose one as a group. The choosing is the valuable part.
"Generate 5 ideas that will solve this problem for the people affected."

        
Pitch it
Have it build something you can react to. Then talk about what it got right, what it made up, and what you would test first.
"Build an artifact so I can present the problem and solution to a group of investors."

      

      
Two ideas to leave with: when AI is in the product, plan for a range of outcomes, not just the happy path. When AI is in your workflow, let it prepare the conversation. You still make the call.

    

  


  


  
  

    

      
07 · Make it reusable

      
Set up a Project, then give it skills

      
A Project gives the AI a place to work. Instructions define how it should behave. Skills give it repeatable ways to do specific jobs.


      
A useful mental model: the LLM is the brain, the Project is the room, the instructions are the operating manual, skills are the SOPs, and tools are the hands. The analogy is not exact, but it helps you see what is missing when an answer disappoints you.


      

        
Create a folder
Give one product, initiative, or recurring workflow a home. Add only the files that help with that work: the product goal, research, glossary, decisions, and current constraints.

        
Create the instructions your harness expects
Write who the AI is helping, what good work looks like, what sources it should trust, how it should respond, and when it must ask instead of assume. The filename depends on the harness. Common examples include AGENTS.md, CLAUDE.md, and GEMINI.md. Some hosted AI Projects keep these instructions in the Project settings instead of a file.

        
Add skills and tools
Add one skill for each repeatable job. Connect only the tools the work needs, such as web search or approved files. Start small, test the output, and improve the instructions when you find a gap.

  2. List the inputs. State what files, context, or answers it needs.
    3. 
            
  3. Write the steps. Put the reasoning process in a sensible order.
    4.
